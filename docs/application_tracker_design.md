# 投递进度追踪 Agent —— 设计文档（Phase 2，MVP 之后实现）

> 状态：设计已想清楚，代码不动。定位：第二个 agent 模块，与面试复盘共享"公司-岗位"实体。
> 砍掉它的理由（面试叙事）：功能蔓延会稀释核心价值（评测体系），
> 参见 docs/competitive_analysis.md 中 EasyWork（全功能但 2 star）的教训。

## 一、需求

投递多个岗位后进度混乱，Excel 手动维护成本高。
用户用自然语言补充进展（"昨天字节约了一面"），系统自动归档到对应公司-岗位，
维护状态机并展示时间线。

用户证据：师兄案例（访谈提纲需追加一题验证）。

## 二、与核心模块的连接（产品叙事关键）

- 投递追踪的「公司-岗位」实体 = 面试复盘录音的「公司-岗位」
- 追踪器知道"下周有三面"，复盘工具知道"前两面哪里答得差"
- 两者结合 = 求职过程的结构化数据底座，而非两个孤立工具

## 三、技术链路

一句话输入 → LLM 结构化抽取（JSON Schema）→ 实体匹配/消歧 → 状态机更新 → 时间线视图

### 事件 Schema（一次输入可含多个事件）

```json
{
  "events": [
    {
      "company": "阿里巴巴",
      "position": "产品经理实习",
      "event_type": "投递 | 笔试 | 约面 | 面试通过 | 面试未过 | offer | 淘汰",
      "round": "一面 | 二面 | 三面 | HR面 | null",
      "date": "YYYY-MM-DD（相对时间需解析：上周三/昨天）",
      "raw_text": "用户原话（溯源用）"
    }
  ]
}
```

### 状态机

投递 → 笔试 → 一面 → 二面 → 三面 → HR面 → Offer / 淘汰
每次状态变化记录 {旧状态, 新状态, 事件日期, 依据原文}，历史不可覆盖。

## 四、四个真实难点（= 面试素材 + 评测指标来源）

1. **实体消歧**："阿里/阿里巴巴/淘天"同一家；同名岗位多部门。
   方案：别名表 + embedding 相似度 + 低于阈值人工确认。
   **原则：agent 拿不准就问，绝不猜（human-in-the-loop）。**
2. **隐式时间解析**："上周三/昨天" → 相对日期计算。纯 prompt 常见失败点，进评测集。
3. **状态冲突**：先报"挂了"又报"约二面" → 提示冲突，不覆盖，保留历史。
4. **事件漏抽**：一句话多事件（"一面过了且约了二面"）→ Schema 支持事件数组。

## 五、评测指标（并入现有评测体系）

- 事件抽取准确率（type/round/date/company 全对才算对）
- 归档准确率（事件落到正确的公司-岗位记录）
- 冲突识别率

## 六、最小实现范围（届时 2–3 天）

- 一个输入框 + SQLite 两张表（application / application_event）
- LLM 抽取 + 消歧确认对话 + 时间线列表
- 不做：投递看板、浏览器扩展、云端公司库（EasyWork 已做，且非核心）
